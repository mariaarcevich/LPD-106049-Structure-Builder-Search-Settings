Dev Notes

  1. 1

    Two Independent Index Options

    • Searchable → indexes the Text form (analyzed, language-aware) for full-text search.
    • Filterable → indexes the Keyword form (value as-is) for filters, sorting and facet counts.

    Both checked → both forms are indexed (not possible today). Both unchecked → the field is not indexed, so no extra on/off option is needed. Note: here Searchable means full-text only; Filterable also covers sorting and facet counts.

  2. 2

    Defaults by Field Type

    Preset when the field is created, so most editors never need to touch them:

    • Text: Searchable and Filterable.
    • Long Text, Rich Text: Searchable only.
    • Select from List, Date, Date and Time, Numeric, Decimal, Boolean: Filterable only.

    Migration keeps today's behavior: Keyword → Filterable, Text → Searchable.

  3. 3

    Changes Still Need a Reindex

    Changing an option on a field that already has content only affects new and edited content; existing content needs a reindex that only administrators can run (Control Panel > Search > Index Actions).

    No persistent message in the Advanced tab (LPD-106049). Same pattern as the existing "Delete Fields" modal:

    • On change: on a published structure, unchecking Searchable / Filterable when it is currently enabled opens a "Change Search Settings" warning modal whose copy follows the option: "Changing this setting may break search (Searchable) / filtering (Filterable) where this field is currently used once the content structure is published. Are you sure you want to continue?" Enabling an option or reverting an unpublished change shows nothing. Cancel reverts the checkbox; "Do not show me this again." skips it for later changes.
    • On publish: the existing "Publish Content Structure Changes" danger modal also covers these changes, naming what changed (search settings, filter settings, or search and filter settings): "You have made changes to the search settings that may affect existing content once published. Be aware that results may be inconsistent until you reindex existing content (or, without Search Admin access: until an administrator reindexes existing content). Are you sure you want to continue?" (New and edited content uses the new settings, older content the previous ones.) No link here. Cancel / Publish.
    • After publishing: reindexing before publishing does nothing, so the follow-up comes now. The success toast carries the next step and stays until closed: users who can reindex (Search Admin access) get "Reindex in Index Actions…" with a direct link that opens in a new window; everyone else gets "Ask an administrator to reindex this content structure…", with no link.
    • Reindex Pending: the structure shows a "Reindex Pending" warning label (next to its title here, and ideally in the Content Structures list) until existing content is reindexed. Its tooltip gives the path to admins ("Reindex it in Control Panel > Search > Index Actions") and tells other users to ask an administrator. Admins could also be notified automatically.
  4. 4

    No Language Selector

    The per-field language selector is removed.

    • Localizable fields: each translation is analyzed with its own language.
    • Non-localizable fields: use the content's language. If it can't be determined, fall back to the default language of the Space (or site) where the content is created, and to the instance default language only as a last resort.
  5. 5

    No Per-Field AI Search Option

    Removed on purpose. Semantic search builds one embedding per content item from several fields, so an AI option on each field doesn't match how it works, and editors can't judge which fields matter or what they cost. If control is needed, it would live at structure level (e.g. "Fields Used in AI Search"). TBD.

Dev Notes

  1. 1

    Searchable Always Indexes Both Forms: Keyword and Text

    When a field is searchable, the search framework must always index it in both forms at the same time:

    • Keyword (value stored as-is): filters, sorting and facet counts.
    • Text (analyzed: tokenized, accent/plural folding, language-aware): full-text search.

    The Keyword vs Text choice is removed from the UI. Since both forms always exist, there is no index-type setting left to change, so a configuration change can never require a full reindex and can never break Collections, facets or Headless queries that filter or sort by this field.

    Turning Searchable on or off never asks for a manual reindex: new and edited content applies immediately, and existing content is caught up by a scheduled background task that administrators can view, schedule and cancel. Structure editors never need Search Admin access.

    Turning Searchable on: no message in the Advanced tab and no confirmation. After publishing, an informative "Content Structure Published" modal (info tone, single Done button) says: "You have made changes to the search settings. These updates are processed in the background and will take some time to fully apply."

    Turning Searchable off: on a published structure, unchecking a currently searchable field opens a "Change Search Settings" warning modal (same pattern as "Delete Fields") says: "Changing this setting may break search and filtering where this field is currently used once the content structure is published. Are you sure you want to continue?" (Searchable covers both here). Cancel reverts the checkbox; "Do not show me this again." skips it for later changes. On publish, the existing "Publish Content Structure Changes" danger modal also covers it: "You have made changes to the search settings that may affect existing search, filters, and Collections. Once published, these updates are processed in the background and will take some time to fully apply. Are you sure you want to continue?"

    Trade-off: loses the "filter only" case (e.g. internal codes) and depends on the Search team confirming the extra index cost is acceptable. Migration: existing Keyword or Text fields become Searchable with both forms.

  2. 2

    No Per-Field AI Search Option

    Removed on purpose. Semantic search builds one embedding per content item from several fields, so an AI option on each field doesn't match how it works, and editors can't judge which fields matter or what they cost. If control is needed, it would live at structure level (e.g. "Fields Used in AI Search"). TBD.
